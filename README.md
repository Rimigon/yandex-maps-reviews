# Прототип: Laravel + Vue, отзывы с Яндекс.Карт

Сервис подключает карточку организации на Яндекс.Картах и показывает её отзывы,
средний рейтинг и счётчики. Парсинг идёт по внутреннему API карточки, потому что
официального API у Яндекса нет.

Демо-доступ (после `php artisan db:seed`): **test@example.com / password**

---

## Что внутри

| Слой | Решение |
|---|---|
| Бэкенд | Laravel 12, PHP 8.2+ |
| Аутентификация | Sanctum, режим SPA (сессионная cookie) |
| Фронтенд | Vue 3 (Composition API) + Vue Router + Tailwind 4, сборка через Vite |
| БД | SQLite для локального запуска, MySQL в docker-compose |
| Очередь | database-драйвер, выгрузка отзывов идёт джобой |

Два главных экрана и одна внутренняя страница:

1. **Вход** — один сид-пользователь, регистрации нет.
2. **Настройки** — вставка ссылки на карточку, список подключённых организаций,
   прогресс выгрузки, обновление и удаление.
3. **Отзывы организации** — рейтинг, число оценок, число отзывов, список отзывов
   по 50 на страницу, история выгрузок с дельтой «было → стало».

Что грузится за один раз: сами отзывы отдаются из базы по 50 штук
(`/api/organizations/{id}/reviews?page=N`), поэтому листание страниц не ходит
в Яндекс. Внешний источник опрашивается один раз при подключении карточки или
при явном обновлении — дальше данные лежат в БД и работают как кэш
(`YANDEX_MAPS_CACHE_TTL`: пока данные свежие, повторный парсинг без `force`
не запускается).

---

## Как парсим Яндекс.Карты

### Почему не сразу headless-браузер

Браузер поднимает Chromium, проходит капчу и «прокручивает» страницу — это
работает, но на каждой карточке занимает секунды и сотни мегабайт памяти.
На сети из 50 филиалов это неприемлемо: 50 браузеров вместо 50 HTTP-запросов.

Поэтому основной путь другой, и он оказался и быстрее, и устойчивее: страница
карточки рендерится на сервере, а вкладка отзывов подтягивает данные через
собственный ajax-метод Яндекса:

```
GET https://yandex.ru/maps/api/business/fetchReviews
    ?ajax=1
    &businessId=<id организации>
    &page=1&pageSize=50&ranking=by_time
    &csrfToken=<токен со страницы>
    &sessionId=<id сессии аналитики со страницы>
    &s=<подпись запроса>
```

Ответ — обычный JSON со страницами по 50 отзывов:

```json
{"data": {"params": {"count": 5859, "totalPages": 118, "page": 1, "limit": 50},
          "reviews": [{"reviewId": "...", "author": {...}, "rating": 5,
                       "text": "...", "updatedTime": "...", "reactions": {...},
                       "businessComment": {...}}]}}
```

Про дату отзыва: отдельной даты создания в ответе нет, есть только `updatedTime`
(время последнего изменения). Именно её показываем как дату отзыва — при этом
редактировании отзыва отображаемая дата сдвинется вперёд. В БД она лежит в
`reviews.source_updated_at`, чтобы имя не врало про смысл поля.

Чтобы этот запрос прошёл, нужно три вещи, и все три добываются из HTML страницы
карточки (блок `<script type="application/json" class="state-view">`):

1. `csrfToken` — привязан к cookie-сессии и живёт недолго;
2. `sessionId` — идентификатор сессии аналитики;
3. `s` — подпись параметров: строка запроса с отсортированными ключами
   хешируется djb2-xor и переводится в беззнаковое 32-битное число.

Алгоритм подписи восстановлен по бандлу фронтенда Яндекс.Карт и закреплён
тестом на реальном запросе, снятом в браузере
(`tests/Unit/QuerySignerTest.php`): если Яндекс поменяет алгоритм, тест упадёт
раньше, чем это станет проблемой в бою.

Итог по времени: 12 страниц отзывов (≈600 записей) — около 13 секунд, без
браузера, с паузами между запросами.

### Что отдаёт Яндекс на самом деле

Отзывов на карточке может быть 5859, но `pageSize` фактически ограничен 50, а
выдача обрывается примерно на 600 отзывах: тринадцатая страница приходит пустой
при любом `count`. Поэтому глубина выгрузки ограничена (`YANDEX_MAPS_MAX_PAGES`,
по умолчанию 12), а не «крутим до пустого ответа» — иначе на каждую карточку
уходило бы 100+ бесполезных запросов.

### Устойчивость к смене разметки

Требование №1: парсер не должен молча возвращать пустоту. Здесь это устроено так:

- **Нет `state-view` блока** → `LayoutChangedException`: страница выглядит иначе,
  чем мы ожидаем.
- **В блоке нет `csrfToken` / `ratingData` / `count`** → та же ошибка с указанием,
  чего именно не хватает.
- **Ответ метода отзывов не похож на прежний** (нет `data.reviews`, нет
  `data.params.count`) → `LayoutChangedException`.
- **Капча в ответе** (маркеры `showcaptcha`, `SmartCaptcha`, `captcha-page`, тип
  ответа `captcha`) → `BlockedException`.
- **403/429** → `BlockedException`, а не «ноль отзывов».
- **Пустая страница** — это нормальный конец выдачи, а не ошибка: так помечена
  только ситуация «данные есть, но разобрать нечего».
- **HTTP 400** — приходит на неверную подпись или лишний параметр (проверено
  на практике: запрос с пустым `host_config=` Яндекс отклоняет, без него —
  принимает). Поэтому в коде есть правило «не отправлять пустые значения»,
  а тело ответа пишется в лог для разбора.

Отдельно разведены две ситуации, которые легко перепутать:

| Что случилось | Что увидит пользователь | Исключение |
|---|---|---|
| Страница недоступна (нет сети, таймаут) | «Не удалось соединиться с Яндекс.Картами» | `YandexMapsException` |
| Карточки по ссылке нет | «По ссылке не нашлось карточки организации» | `OrganizationNotFoundException` |
| Яндекс сменил разметку | «Не удалось разобрать страницу карточки: …» | `LayoutChangedException` |
| Нас заблокировали | «Яндекс.Карты показали капчу…» / «отклонили запрос (HTTP 403)» | `BlockedException` |

Карточки нет и сломанная разметка — разные вещи: на несуществующую организацию
Яндекс отдаёт **HTTP 200** и обычную страницу карт с текстом «Ничего не найдено»,
без данных организации. Парсер это распознаёт (проверено вживую) и говорит, что
карточки нет, а не что «парсер сломался». Технические подробности (статус, тело
ответа, текст ошибки соединения) пишутся в лог, а не в интерфейс.

Каждая ошибка пишется в лог с id организации и текстом, а `sync_status`
переводится в `failed`, поэтому поломка видна и в интерфейсе, и в БД.

Дополнительно рейтинг и счётчики читаются из микроразметки schema.org
(`<meta itemprop="ratingValue">`) — если внутреннее состояние карточки
переименуют, но микроразметка останется, рейтинг всё равно подтянется.

### Запасной путь: headless-браузер

Если Яндекс всё-таки закроет прямой путь, есть готовый обход:
`browser-fallback/collect-reviews.mjs` (Node + playwright-core). Он открывает
карточку как обычный посетитель, слушает ответы `fetchReviews` и возвращает HTML
страницы вместе с перехваченными страницами отзывов — их разбирают те же
парсеры, что и в основном пути.

Включается переменной:

```
YANDEX_MAPS_BROWSER_FALLBACK=true
```

Важно про окружение: сборщик запускается как отдельный процесс, поэтому там,
где работает воркер, должны быть `node` и `playwright-core`
(`cd browser-fallback && npm install`). В образ из `docker-compose` Node с
Chromium не входит: это +200 МБ к образу ради аварийного пути, который по
умолчанию выключен. Нужен запасной путь в докере — поднимите рядом сервис на
образе `mcr.microsoft.com/playwright` с этим каталогом и запустите сборщик там.

Логика выбора: сначала всегда пробуем прямой HTTP-путь, и только если он упал
(капча, 403/429, смена защиты) и запасной путь включён — запускается браузер.
Проверка самого сборщика без обращения к Яндексу (на локальном сервере-двойнике):

```bash
cd browser-fallback && npm install && node self-check.mjs
```

### Сравнение подходов

| | Внутренний JSON API | Headless-браузер |
|---|---|---|
| Скорость | ~13 с на 600 отзывов | ~6 с на 71 отзыве, дольше на крупной карточке (растёт с объёмом) |
| Ресурсы | один HTTP-клиент | 300+ МБ на браузер |
| Хрупкость | подпись `s` и csrf-токен могут измениться | вёрстка и названия классов |
| Капча | может отдать капчу на прямые запросы | проходит проверку как живой пользователь |
| Объём (50 филиалов) | 50 фоновых джоб | нужен пул браузеров, дорого |

Вывод: основной путь — JSON API, браузер держим как аварийный, а не как основной.

## Ответы по пунктам «Дополнительных требований»

**1. Устойчивость к смене разметки.** Разбор не привязан к CSS-классам: данные
берутся из JSON состояния страницы и из микроразметки. Любое несоответствие
ожидаемой структуре — это исключение `LayoutChangedException` с описанием,
чего не хватило, а не пустой список. Исключение логируется и попадает в
`organizations.sync_error`, который виден в интерфейсе. Что я считаю главным
признаком поломки: страница отдаётся (HTTP 200), но в ней нет блока
`state-view`, либо в ответе метода отзывов исчезли `data.reviews`/`params.count`,
либо отзывы есть, а ни у одного нет `reviewId`.

**2. Обоснование подхода.** См. раздел выше: JSON API против браузера, плюсы,
минусы, риски. Главный риск — подпись `s` и короткоживущий csrf-токен; он
закрыт фиксирующим тестом и поддержкой обновления токена (Яндекс умеет вернуть
новый токен вместо данных — такой ответ распознаётся и запрос повторяется).

**3. Масштаб и фоновая обработка.** Выгрузка вынесена в джобу
`SyncOrganizationReviewsJob` (очередь, `tries=3`, бэкофф 30/120/300 с,
`timeout=600`). В HTTP-запросе остаётся только постановка задачи: пользователь
получает 201 сразу, а прогресс видит на странице организации — фронт опрашивает
`/api/organizations/{id}` раз в 1.5 секунды, пока `sync.status` = `queued|running`,
и рисует полосу «страница N из M». Поля прогресса лежат в самой организации
(`sync_status`, `sync_pages_done`, `sync_pages_total`, `sync_error`), поэтому
отдельная таблица задач не нужна. Каждая попытка джобы открывает новую сессию,
то есть заходит с другим User-Agent и прокси. Для 50 филиалов: 50 джоб в
отдельной очереди (`YANDEX_MAPS_QUEUE`) и пул воркеров под неё.

**4. Анти-бан на объёме.** В коде уже есть:
- пауза между запросами (`throttle_ms`, по умолчанию 250–900 мс; пауза
  случайная, чтобы запросы не шли равномерным потоком);
- выбор User-Agent и прокси на сессию парсинга из списков
  (`YANDEX_MAPS_USER_AGENTS`, `YANDEX_MAPS_PROXIES`) — то есть на каждую
  карточку новый «отпечаток» клиента;
- повторы с линейным бэкоффом на сетевые сбои и на 5xx;
- распознавание блокировки: капча, 403 и 429 — отдельное исключение, которое
  не маскируется под «нет отзывов»;
- cookie-сессия живая в пределах одной карточки, поэтому Яндекс видит один
  последовательный визит, а не набор разрозненных запросов.

Чего нет и что я добавил бы при реальной нагрузке: свой per-host лимитер
(например, Redis-токен-бакет на 1 запрос в 2 секунды на прокси), очередь
исходящих запросов на каждый прокси, автоматическое отключение прокси после
серии 403, и «холодный» путь — при капче не долбить повторно, а откладывать
карточку на 15–30 минут (сейчас джоба просто уходит в бэкофф 30/120/300 с).
Ещё: выгрузку лучше ставить в окна низкой активности и распределять 50 филиалов
по времени, а не запускать все сразу.

**5. Идемпотентность и история.** Отзывы пишутся `upsert` по паре
`(organization_id, external_id)`, где `external_id` — `reviewId` из Яндекса.
Дублей не будет ни при повторной выгрузке, ни при гонке двух джоб. У каждой
записи есть `content_hash` отпечаток изменяемых полей (автор, оценка, текст,
ответ компании, реакции, дата) — по нему считается, что отзыв реально
изменился, а что просто пришло повторно. После каждой выгрузки пишется снимок
`organization_snapshots` (рейтинг, счётчики, сколько добавлено/обновлено и
дельта «было → стало» по каждому показателю); на странице организации есть
таблица истории выгрузок. Модель данных описана миграциями:
`organizations` (карточка и состояние выгрузки), `reviews` (отзывы),
`organization_snapshots` (снимки). Отдельная история правок самого текста
отзыва не ведётся — см. «Что доделал бы».

## Быстрый старт локально

Нужны PHP 8.2+, Composer, Node 20+.

```bash
composer install
npm install
cp .env.example .env
php artisan key:generate
touch database/database.sqlite
php artisan migrate --seed
npm run build            # или npm run dev для разработки
```

Дальше нужны два процесса:

```bash
php artisan serve        # http://127.0.0.1:8000
php artisan queue:work   # воркер очереди, без него выгрузка не пойдёт
```

Логин и пароль печатает сидер (`SEED_USER_EMAIL` / `SEED_USER_PASSWORD`,
по умолчанию `test@example.com` / `password`).

### Запуск через docker-compose

```bash
docker compose up --build
```

Поднимается приложение (http://localhost:8080), MySQL и фоновый воркер. Перед
запуском положите `APP_KEY` в `.env` (`php artisan key:generate --show`),
порт меняется переменной `APP_PORT`.

### Проверка парсера из консоли

```bash
php artisan yandex:sync "https://yandex.ru/maps/org/.../1234567890/reviews/"
```

Команда выгружает отзывы синхронно, печатает таблицу с рейтингом и счётчиками
и не требует поднятого воркера — удобно, чтобы проверить парсер после изменений.
В docker-compose то же самое:

```bash
docker compose exec app php artisan yandex:sync "https://yandex.ru/maps/org/.../1234567890/reviews/"
```

### Тесты

```bash
php artisan test
```

Покрыто: разбор ссылок, подпись запросов (на реальном запросе из браузера),
разбор страницы карточки и отсутствующей карточки, разбор ответа метода отзывов,
капча и смена разметки, недоступный источник и карточка без отзывов,
идемпотентность и обновление отзывов, снимки «было → стало», API авторизации
(401 с заголовком Accept и без него) и доступа к чужой организации, добавление
организации с постановкой в очередь, выгрузка через headless-браузер, доверие к
заголовкам reverse proxy. Всего 58 тестов, они работают на фикстурах и не ходят
в живой Яндекс, поэтому запускаются без сети.

## Docker: как устроено

| Контейнер | Что делает |
|---|---|
| `app` | PHP 8.3, встроенный сервер Laravel, раздача SPA и API |
| `queue` | Тот же образ, но запускает `php artisan queue:work` |
| `db` | MySQL 8 |

Запасной сбор через браузер в compose не входит: Chromium в образе нужен
только тогда, когда включён `YANDEX_MAPS_BROWSER_FALLBACK`, а по умолчанию он
выключен и основной путь работает без него. Если запасной путь нужен, ставьте
`node` и `playwright-core` рядом с приложением (`browser-fallback/npm install`).

Переменные окружения — в `.env` (и в `.env.example` как образец). Ключевые:

| Переменная | Смысл |
|---|---|
| `YANDEX_MAPS_MAX_PAGES` | сколько страниц отзывов забирать (Яндекс отдаёт ~12 по 50) |
| `YANDEX_MAPS_THROTTLE_MIN_MS` / `_MAX_MS` | пауза между запросами, анти-бан |
| `YANDEX_MAPS_USER_AGENTS` | список User-Agent'ов через `\|`, выбирается на сессию |
| `YANDEX_MAPS_PROXIES` | прокси через запятую, `http://user:pass@host:port` |
| `YANDEX_MAPS_CACHE_TTL` | сколько секунд считать данные свежими (повторный парсинг без `force` не запускается) |
| `YANDEX_MAPS_QUEUE` | имя очереди для выгрузок |
| `YANDEX_MAPS_BROWSER_FALLBACK` | включает запасной сбор браузером |
| `SANCTUM_STATEFUL_DOMAINS` | домены, для которых Sanctum включает сессию; нужен локальному запуску (по умолчанию `localhost:8000`) |
| `TRUSTED_PROXIES` | адреса reverse proxy (или `*`), если TLS заканчивается на нём; иначе Laravel видит http |
| `APP_PORT`, `DOCKER_APP_URL`, `DOCKER_SANCTUM_DOMAINS`, `DOCKER_TRUSTED_PROXIES`, `DOCKER_DB_*` | читает только docker compose; подробно — в разделе «Деплой на хостинг» |

```
tests/Unit, tests/Feature, tests/Fixtures       тесты и образцы страниц
```

Контроллеры не знают про парсинг: они вызывают `OrganizationSyncService` или
ставят джобу, а вся работа с внешним источником лежит в `Services/YandexMaps`.

## Деплой на хостинг

### Вариант 1: VPS с Docker (рекомендуемый)

Подходит и для чужого сервера (например, у знакомого), но там есть особенности —
см. следующий подраздел.

```bash
# на сервере
git clone <репозиторий> && cd yandex-maps-reviews
cp .env.example .env
php -r "echo 'APP_KEY=base64:'.base64_encode(random_bytes(32)).PHP_EOL;"   # или php artisan key:generate --show локально
```

В `.env` рядом с `compose.yaml` обязательно задать:

```
APP_KEY=base64:...
APP_PORT=8080                       # порт, на который смотрит reverse proxy
DOCKER_APP_URL=https://reviews.example.com
DOCKER_SANCTUM_DOMAINS=reviews.example.com
DOCKER_TRUSTED_PROXIES=*            # если TLS заканчивается на вашем nginx/Caddy
DOCKER_DB_PASSWORD=<свой пароль>
DOCKER_DB_ROOT_PASSWORD=<свой пароль>
```

`DOCKER_APP_URL` и `DOCKER_SANCTUM_DOMAINS` — не то же самое, что `APP_URL` и
`SANCTUM_STATEFUL_DOMAINS` выше по файлу: первые читает только docker compose,
вторые — локальный запуск. Без правильного домена в `DOCKER_SANCTUM_DOMAINS`
вход вернёт 500 «Session store not set on request»: Sanctum включает сессию
только для запросов со своего домена и определяет его по Origin/Referer.
Если к домену нестандартный порт, он входит в значение: `reviews.example.com:8080`.

```bash
docker compose up -d --build     # первый запуск: миграции и сидер выполняет контейнер app
```

Дальше смотрим в docker compose ps, чтобы `app`, `queue` и `db` были живы, и
проверяем парсер: `docker compose exec app php artisan yandex:sync "<ссылка>"`.

Для HTTPS — любой reverse proxy (Caddy или nginx + certbot) на порт `APP_PORT`.
Когда TLS заканчивается на прокси, приложение получает обычный HTTP, поэтому
адрес прокси нужно указать в `TRUSTED_PROXIES` (или `DOCKER_TRUSTED_PROXIES`
для compose). Без этого Laravel считает запросы небезопасными: ссылки идут с
`http`, а cookie сессии не получает флаг `Secure`. Значение `*` означает
«доверять всем» и подходит, если приложение доступно только через ваш прокси;
если порт выставлен наружу напрямую, перечислите адреса через запятую.

Обновление версии: `git pull && docker compose up -d --build` (миграции применятся
сами, сидер идемпотентный).

### Деплой на чужой VPS

Технически это тот же вариант 1. Отличия, которые стоит учесть заранее.

**Своя база и свой порт.** Сервер общий, поэтому: отдельная база
(`DOCKER_DB_DATABASE`), отдельный пользователь БД и свой порт (`APP_PORT`),
чтобы не занять чужой. Контейнеры и том называются с префиксом имени каталога,
поэтому с чужими сервисами не пересекаются:

```bash
docker compose ps                 # видно только свои контейнеры
docker compose down               # останавливает только их, не трогая остальное
```

Если на сервере уже есть nginx или Caddy на 80/443, публикуйте приложение на
свободный порт и проксируйте на него через чужой reverse proxy, а не пытайтесь
занять 80/443 сами.

**Чужой IP — это чужой отпечаток для Яндекса.** Парсер ходит в Яндекс с адреса
сервера. Если Яндекс начнёт отдавать капчу или 403, под удар попадает весь IP,
а не только этот проект: это может задеть другие сайты знакомого. Поэтому:
не поднимать `YANDEX_MAPS_THROTTLE_MIN_MS` ниже значения по умолчанию, не
увеличивать `YANDEX_MAPS_MAX_PAGES`, а для регулярного парсинга лучше добавить
прокси (`YANDEX_MAPS_PROXIES`) и предупредить владельца сервера.

**Доступ к `.env`.** Тот, у кого есть доступ к серверу, может прочитать `APP_KEY`
и пароли БД. Для тестового задания это нормально, но не кладите туда ничего
личного, а пароли БД задайте отличные от дефолтных.

**Память.** Контейнерам нужно примерно 500–700 МБ (PHP + MySQL). Если на сервере
мало свободной памяти, приложение можно поднять без MySQL: переведите Laravel на
SQLite (`DB_CONNECTION=sqlite`, `DB_DATABASE=/var/www/html/database/database.sqlite`)
и остановите `db`. Учтите, что в контейнере без тома файл базы теряется при
пересборке, поэтому для долгого хранения всё же лучше MySQL с томом `db-data`.

**Без домена.** Если домена нет, приложение открывается по `http://<IP>:<порт>`,
и в `DOCKER_SANCTUM_DOMAINS` указывается `<IP>:<порт>`. Для тестового задания
этого достаточно, но HTTPS предпочтительнее: без него cookie сессии идёт открытым
текстом.

**Если TLS на чужом nginx.** Тогда добавьте `DOCKER_TRUSTED_PROXIES` со списком
адресов прокси или `*`, если порт приложения не выставлен в интернет напрямую.
Проверяется одной строкой: запрос с `X-Forwarded-Proto: https` должен давать
`https` в схемах (см. тест `TrustedProxiesTest`).


### Вариант 2: обычный shared-хостинг (PHP + MySQL)

```bash
# локально
composer install --no-dev --optimize-autoloader
npm ci && npm run build     # public/build попадёт в архив
```

Дальше выгрузка файлов (без `node_modules`, `.env`, `tests`), на сервере:
создать БД и `.env` (`APP_ENV=production`, `APP_DEBUG=false`,
`QUEUE_CONNECTION=database`, `SANCTUM_STATEFUL_DOMAINS=<домен>`), затем
`php artisan migrate --force && php artisan db:seed --force`. Воркер очереди
запускается cron-ом (`php artisan queue:work --stop-when-empty`), либо оставьте
`QUEUE_CONNECTION=sync`: тогда выгрузка идёт прямо в HTTP-запросе, и воркер не
нужен вообще. Для одной-двух карточек это приемлемо (600 отзывов ≈ 13 секунд
ожидания), для сети филиалов — нет.

   значениями: сейчас видно, что отзыв изменился, но не видно, что именно было
   написано раньше.
4. **Парсинг через браузер как второй источник с автоматическим переключением по
   счётчику ошибок** (сейчас переключение разовое, внутри одной попытки).
